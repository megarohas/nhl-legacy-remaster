# Правка сейвов франшизы

Сейв на приставке — пакет STFS `CON` (парные хеш-таблицы) с одним файлом внутри.
Внутренний файл франшизы:

| Смещение | Что |
|---|---|
| `0x00` | `Dynasty` (16 байт с нулями) |
| `0x10` | checksum_a — CRC-32/IEEE по `[0x1C..конец файла]`, big-endian |
| `0x14` | версия = 3 |
| `0x24` | размер базы |
| `0x28` | checksum_b — CRC-32/BZIP2 по базе `[0x2C..0x2C+размер]`, big-endian |
| `0x2C` | база TDB v6 (48 таблиц франшизы: `leaguestates`, `leagueplayerbiotable`, …) |
| дальше | хвост 360 008 байт (не TDB, не трогаем) |

Суммы проверены на всех четырёх своих сейвах; перезапись без правок даёт
побайтово исходный файл.

## Как править

```bash
# 1. достать внутренний файл
python tools/stfs.py extract "game/raw/…/DYNASTY 20240213195118A" game/extracted/saves/X
# 2. посмотреть и поменять leaguestates (TYPE KEY VALUE …) — CRC пересчитываются сами
python tools/tdb.py states   "game/extracted/saves/X/DYNASTY 20240213195118A"
python tools/tdb.py setstate "…/DYNASTY 20240213195118A" out.inner 13 78 2025
# 3. положить обратно в пакет с перехешированием STFS
python tools/stfs.py replace "game/raw/…/DYNASTY 20240213195118A" "DYNASTY 20240213195118A" out.inner "game/work/DYNASTY 20240213195118A"
python tools/stfs.py verify  "game/work/DYNASTY 20240213195118A"
```

Подпись пакета CON (RSA приставки) после правки недействительна. Розничная
приставка такой сейв не примет; на RGH подписи контента, как правило, не
проверяются — подтверждается только опытом.

**Правка сейва франшизы в порте NHL 13 в целом работает, но не всякая (09.10.2026).** Принимаются: правка
`leaguedraftpick.year` у nhl13-franchise (+14 у живых строк, сейв проходит драфт-2027), ROSTER-сейв с 2251
правкой и контрольная правка одного `leaguedraftpick.year` в корне draftpool. Отвергнуты с «… appears to be
damaged and cannot be used» правки draftpool в копии того же сейва ([draft-pool.md](draft-pool.md) §4):
- номер одного игрока НХЛ в `leagueplayerbiotable` (72 → 73; в его записи состава остался 72);
- пул `leaguerookiedata`, сжатый до 147 или с переростками в списке удалённых, и `isdraftable` = 0 у 1249
  игроков.
Все суммы при этом верны (`tdb verify` OK). Видимо, при загрузке игра проверяет согласованность таблиц.
Кандидаты: номер в био и в `leaguerostertable`, ссылки `leaguescoutvisits.playerid` на класс. Само правило не
найдено. Значит, правка должна сохранять связи между таблицами, и каждую новую правку нужно проверять загрузкой.

## Живые записи: удалённые и запас

Таблица сейва — не только записи. Заголовок таблицы (все поля u16):

| Смещение | Что |
|---|---|
| `+0x14` | max — мест в таблице |
| `+0x16` | current — занято мест с начала, вместе с удалёнными |
| `+0x18` | число удалённых записей |
| `+0x1A` | голова списка свободных (0xFFFF — пусто) |

У удалённой записи первые 16 бит — номер следующей свободной (0xFFFF — конец). Они накрывают поля из
начала записи: у `leaguerostertable` это `team` (биты 4…10), поэтому удалённая запись состава
«переезжает» в чужую команду (отсюда «team 55/56», «DAL 38», «SPR 52» в разборе франшизы Legacy). Остальные поля остаются
от прежней записи: например, у удалённых `leagueplayerbiotable` — прежние `artid`, `game_id`, `hasportrait`.
Места `[current, max)` — запас, не записи: там байты 0xDB (у `leaguerostertable` они читаются как `team`
94, у `leagueplayerbiotable` NHL 13 — `proteam` 29) или остатки прежних записей (у франшизы Legacy после
межсезонья: календарь, статистика матчей, `leaguestates`). У таблиц alloc 2/6 `tools/tdb.py` считает
`rows` = max, поэтому записи — только **`Tdb.live_rows(таблица)`**: `[0, current)` без удалённых
(`Tdb.deleted` — список в порядке цепочки; цепочка проверяется: длина = счётчику, без циклов, номера < max).
`column(…, live_only=True)`, `is_live`, `dead_rows`, `counts`; у `tools/tdb_read.py` — `live_rows`,
`column(…, live_only=True)`. Сводка по файлу — `python tools/tdb.py live FILE [TABLE …]`.

В базах игр и всех наших базах max = current и удалённых нет: там `live_rows` = все строки. В сейвах
(копии 09.10.2026): ROSTER пользователя — удалённых нет, запас 16 621 строка в 27 таблицах (у
`exhibitionplayerbiotable` 1534, `exhibitionskaterequipment` 1532, `exhibitionrostertable` 4847 — с `team`
219); франшизы NHL 13 (15 сейвов пользователя, 2 тестовых) — запас 240–260 тыс. строк, удалённые в 4 (составы 22–39,
`leagueplayerlateststats` до 1331, `leaguetradeblock` до 70, `leaguecontractoffers` 6); франшизы Legacy — до
2209 удалённых (`leaguetradeblock` 1570, `leaguerookiedata` 1008, составы до 217, по 95 у био, атрибутов и
экипировки ушедших игроков). Кто пишет в сейв по номеру строки (`roster.equipment roster`, `photos.py save`,
`tdb.py setstate/set`), берёт только живые записи; запись в 0xDB-запас игра не прочтёт, а запись в удалённую
может испортить список свободных.

## Ключи `leaguestates`

| type / key | Смысл |
|---|---|
| 0 / 0 | дата лиги, дни от 30.12.1899 |
| 13 / 78 | год сезона |
| 15 / 90 | минимальная зарплата |
| 18 / 108 | нижний порог платёжной ведомости |
| 19 / 114 | потолок зарплат |
| 20 / 120 | 30 — вероятно, число команд |
| 23 / 138 | матчей в сезоне |

Годы в базе — 8 бит + 1900 (`leagueplayerbiotable.year`, `leaguedraftpick.year`,
`yearufa`…); 219 похоже на метку «пусто». За сезоны игра сама сдвигает год, дату,
финансы и годы драфт-пиков; годы рождения не меняются.

## Опыт 1 (собран 07.10.2026, ещё не загружен)

`game/work/DYNASTY 20240213195118A` — из сейва 13.10.2012:

- дата 41195 → 45943 (13.10.2025), год 2012 → 2025;
- финансы 2025/26: минималка 775 000, порог 70 600 000, потолок 95 500 000;
- `leaguedraftpick.year` +13 (2013–2018 → 2026–2031);
- годы рождения не трогали: если в игре возраст вырос на 13 лет — возраст
  считается от года лиги.

Вопросы опыта: примет ли приставка пакет без подписи; не пересчитает ли игра
значения обратно; что покажет экран (год, возраст, финансы, календарь).
