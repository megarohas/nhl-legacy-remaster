# Фото игроков: устройство и замена на составы 2026/27

Портреты в меню NHL 13 — маленькие ролики Apt (Flash EA) в контейнере BIGF, внутри одна
текстура DXT5 в формате Xbox 360. Номер файла — поле `artid` игрока, показ фото включает
`hasportrait`. Свежие фото берём с CDN НХЛ (те же адреса, что уже собирает конвейер
составов), перекладываем в кадр EA и кладём рядом с базой в `cache:` — архивы не трогаем.
Инструмент — [tools/playerhead.py](../tools/playerhead.py) (только стандартная библиотека).

Разбор от 07.10.2026; файлы игры — диск без TU2 (в `patch.big` портретов нет). В игре
результат ещё не проверялся.

## Коротко

- Два размера фото на каждого игрока: **большие** `playerheads` (в `nocacherender.big`) и
  **малые** `playerheadssmall` (в `cache.big`), по 6823 номера (p1…p9802) + 4 силуэта.
  Ещё 197 карточек HUT (`cards/playerheads_special`) — это картинки карт, не портреты.
- Номер файла `p<N>.big` = `exhibitionplayerbiotable.artid`. Код игры берёт
  `hasportrait ? artid : 60000 + artid % 4` (четыре силуэта с разными причёсками).
- Папка выбирается по номеру: ≤ 4000 → `p0_4000`, ≤ 8000 → `p4001_8000`,
  ≤ 12000 → `p8001_12000`, больше → `silhouettes` (функция `getArtAssetPath` в ActionScript).
- Файл: BIGF (6 записей, выравнивание 0x40, метка `L286`, 16 байт хвоста) → ролик Apt
  (сцена, геометрия, константы) + текстура XPR2 (TX2D), сжатая RefPack (`10 FB`).
- Текстура: DXT5 (`k_DXT4_5`), тайлинг Xenos, порядок байт 8in16, **без мипов**, альфа
  прямая, под прозрачным — чёрный. Большие — 512×256 (сцена 467×253) или 512×512 (467×260),
  малые — 256×128 (сцена 202×128). Картинка — только на сцене, в левом верхнем углу, 1:1.
- Прототип разбирает и собирает все 13 851 файл байт-в-байт по контейнеру и тайлингу;
  PNG → DXT5 → `.big` повторяет заголовки оригинала, путь через DDS даёт тот же XPR2 байт-в-байт.
- Источник: `https://assets.nhle.com/mugs/nhl/20262027/<TEAM>/<NHL ID>.png` — PNG 336×336
  RGBA с прозрачным фоном; адрес уже есть в `players.json` (`photo`). Нет фото — 302 на
  `default-skater.png`.
- Замена — файлами в `game/userdata/cache/guest/fe/ion/artassets/…` (как `nhlng.db`) и
  `hasportrait = 1` в базе. На 798 игроков НХЛ — 1596 файлов, ≈ 28 МБ.

| Размер | Где (по коду Apt и логу) |
|---|---|
| большие | экран загрузки со стартовыми составами (`03_startinglineups` → `subscreenstartinglineup` через `NHLImageLoader`: в логе 07.10 — `playerheads\p4001_8000\p6840.big` и силуэты `p60000…p60003`); шапка карточки игрока (`playerinfoheader`, `HEAD_ASSET_TYPE = playerHeads`, три масштаба); выкуп контракта во франшизе (`dm_contractbuyout`); `NHLPlayerHeadLoader`, стиль 2 (окно 240×240, сдвиг −90, −158) |
| малые | `NHLPlayerHeadLoader`, стиль 1 (окно 128×128 со сдвигом x + 26 — видна середина сцены 202×128); обменный список франшизы (`tradeblockscreen`); карточки HUT (`cardsmain`: `mPlayerHeadPath = playerHeadsSmall`); экраны онлайн-лиг (MUD) — путь собирает сам код игры (`artAssets/playerHeadsSmall/p0_4000/p%d.swf` в `default.xex`) |

Созданным игрокам компоненты умеют показывать отрисованную 3D-голову (`bIsCustomRender`,
`CUSTOM_RENDER_HEAD`) — к фото это не относится.

## 2. Как игра выбирает файл

### Поля базы

| Таблица | Поле (shortname) | Бит | Что |
|---|---|---:|---|
| `exhibitionplayerbiotable` (`nhlng.db`) | `artid` (`rnOl`) | 14 | номер фото `p<artid>.big`, 0…16383 |
| | `hasportrait` (`LcvS`) | 1 | 1 — фото, 0 — силуэт |
| | `headid` (`DaPp`) | 15 | 3D-голова в матче, к фото не относится |
| `leagueplayerbiotable` (франшиза, копия в сейве) | `artid`, `hasportrait` | 14, 1 | то же в сейве франшизы |
| `exhibitionplayerbiotable` (`draft_roster.db`) | `artid`, `hasportrait` | 14, 1 | заготовки драфта |

`exhibitionteams.artid` и `leagueteams.artid` — логотипы команд, не игроки.

### Код

1. **Номер для интерфейса** (`default.xex`, функции `0x827E0810` и `0x827E0840`, таблица
   `0x8204540C` = 60000, 60001, 60002, 60003): у записи игрока в памяти `artid` — u16 по
   +96, `hasportrait` — байт по +118.

   ```c
   asset_id = hasportrait ? artid : silhouettes[artid % 4];   // 60000 + artid % 4
   ```

2. **Путь** — ActionScript `GeneralHelpers.getArtAssetPath` (`boot.big`,
   `fe/ion/game/pods/helpers/generalhelpers.big`, функция по смещению 0x2074 в Apt Data;
   разобрано своим дизассемблером байткода Apt):

   ```js
   path = "artAssets/" + assetType + "/";            // playerHeads | playerHeadsSmall
   if (!isNaN(id)) {
     if (!(Number(id) > 4000))       path += "p0_4000/";
     else if (!(Number(id) > 8000))  path += "p4001_8000/";
     else if (!(Number(id) > 12000)) path += "p8001_12000/";
     else { trace("playerHeads ID out of range: " + id + ". Looking in silhouettes");
            path += "silhouettes/"; }
   }
   return path + "p" + id + ".swf";
   ```

   Тот же разбор диапазонов — в машинном коде экранов MUD (`0x82DA6514`: `cmpwi 4000/8000/12000`).
3. **Файл**: загрузчик Apt меняет `artAssets/…/X.swf` на `cache:\fe\ion\artassets\…\x.big`
   (нижний регистр). Сначала — свободный файл в `cache:`, потом архив (в логе
   `NtCreateFile FAILED: path='cache:\fe\ion\artassets\playerheads\silhouettes\p60001.big'`
   — это и есть проверка свободного файла). В порте `cache:` — `game/userdata/cache/guest/`.

Следствия:

- `artid` 1…12000 → обычные папки; **12001…16383 → `silhouettes/p<artid>.big`** — свободное
  пространство имён для новых фото (силуэты 60000+ полю в 14 бит недоступны);
- `artid = 0` (180 строк исходной базы) → `p0_4000/p0.big`, такого файла нет — только
  с `hasportrait = 0`;
- `hasportrait = 1` без файла — вероятно, пустое место вместо головы: в исходной базе так
  не бывает ни разу;
- карты HUT и персонал — свои имена (`playerheads_special_<id>`, `heads_staff_<id>`), с
  `artid` не пересекаются.

## 3. Разметка `p<artid>.big`

Большие и малые фото и силуэты устроены одинаково, отличаются числа. Все 13 851 файл
(включая карты HUT) — 6 записей в одном порядке; XPR2-заголовков всего 2 разных у больших
(512×512 и 512×256) и по одному у малых и карт.

### Контейнер BIGF (на примере большого `p1.big`, 23 536 байт)

| Смещение | Поле | Значение |
|---|---|---|
| 0x00 | магия | `BIGF` |
| 0x04 | u32 **LE** — размер без хвоста | 0x5BE0 (23 520) |
| 0x08 | u32 BE — записей | 6 |
| 0x0C | u32 BE — конец заголовка | 0x58 (длиннее, если номера символов длиннее: 0x5A…0x5E) |
| 0x10 | оглавление: u32 BE смещение, u32 BE размер, имя ASCIIZ | `0`, `3`, `sg1`, `2`, `sg2`, `1` |
| 0x50 | метка версии | `L286` + `15 05 00 01` (4 файла — `L287`: p2052, p2053, p8111, p8310) |
| … | нули до 0x80 | данные каждой записи — с адреса, кратного 0x40 |
| 0x80 | `0` | Apt Data, 240 байт (часто сжат RefPack) |
| 0x180 | `3` | геометрия, 288 байт |
| 0x2C0 | `sg1` | пустая метка (смещение = смещение текстуры; у `L287` — своё место 0x40) |
| 0x2C0 | `2` | XPR2, RefPack: 22 783 → 131 168 байт |
| 0x5BC0 | `sg2` | пустая метка (смещение = смещение констант) |
| 0x5BC0 | `1` | Apt constant file, 32 байта |
| 0x5BE0 | хвост, 16 байт | `417a7f2c…` — у каждого файла свой; не MD5/SHA ни содержимого, ни пути (проверено); в размер BIGF не входит |

Метки `sg1`/`sg2`, по-видимому, обрамляют сегмент с текстурой (данные для GPU): между ними
всегда ровно запись текстуры.

### Записи Apt

| Запись | Что |
|---|---|
| `0` | `Apt Data:1:5:4` + `1A 00`; u32 по 0x10 — смещение символа Movie (тип 9, подпись `0x09876543`): +0x1C — число символов, +0x20 — таблица, **+0x24 / +0x28 — ширина и высота сцены**, +0x2C — 1000 мс на кадр, кадр один. Символ Image (тип 7) и Shape (тип 1) |
| `<N>` | текстура символа Image: имя записи = индекс символа + 1 (обычно `2`; бывает `8`, `60`, `566`, `1154` — тогда и Apt Data длиннее) |
| `<N+1>` | геометрия Shape: заливка `FFFFFFFF` текстурой (ссылка — индекс Image), матрица текстуры 1, 0, 0, 1, 0, 0 — **тексель = точка сцены**; два треугольника по 6 вершин (шаг 32 байта): (0, H), (0, 0), (W, 0), (W, 0), (W, H), (0, H) |
| `1` | `Apt constant file` + `1A 00 00`, u32 0x1C, u32 0 констант, u32 0x20 |

То есть сцена W×H показывает левый верхний угол текстуры один к одному, остальное
текстуры (x ≥ 467 или y ≥ 253) не видно никогда.

### XPR2 (распакованная запись текстуры)

| Смещение | Поле | Значение |
|---|---|---|
| 0x00 | магия | `XPR2` |
| 0x04 | u32 BE — размер заголовка после 0x0C | 0x54 (данные с 0x60) |
| 0x08 | u32 BE — размер данных | 0x20000 (512×256), 0x40000 (512×512), 0x8000 (256×128), 0x10000 (карты) |
| 0x0C | u32 BE — ресурсов | 1 |
| 0x10 | ресурс | `TX2D`, смещение 0x20 (→ 0x2C), размер 0x34, имя по 0x18 (→ 0x24) |
| 0x20 | конец таблицы | 0 |
| 0x24 | имя | `strName` (у всех файлов одно) |
| 0x2C | D3DTexture, 13 слов | Common 3 (текстура), ReferenceCount 1, Fence 0, ReadFence 0, Identifier 0, BaseFlush `FFFF0000`, MipFlush `FFFF0000`, константа выборки (6 слов ниже) |
| 0x60 | данные | ровно столько, сколько в 0x08 |

Целиком XPR2 — 131 168 / 262 240 / 32 864 / 65 632 байт.

### Константа выборки GPU (6 слов в D3DTexture)

| | 512×256 | 512×512 | 256×128 | Поля |
|---|---|---|---|---|
| d0 | `84000002` | `84000002` | `82000002` | тип 2 (текстура), знаки 0, wrap; pitch (биты 22–30) ×32 = **512 / 512 / 256**; бит 31 — **тайлинг** |
| d1 | `00000054` | `00000054` | `00000054` | формат 0x14 = **k_DXT4_5**; биты 6–7 = 1 — **8in16**; адрес (биты 12–31) 0 — ставится при загрузке |
| d2 | `001FE1FF` | `003FE1FF` | `000FE0FF` | ширина − 1 (биты 0–12), высота − 1 (биты 13–25) |
| d3 | `00000D10` | `00000D10` | `00000D10` | swizzle 0x688 = RGBA; фильтры 0 (их ставит состояние сэмплера при рисовании) |
| d4 | `00000000` | `00000000` | `00000000` | мип-уровни 0…0 — **мипов нет** |
| d5 | `00000A00` | `00000A00` | `00000A00` | размерность 1 = 2D, packed mips 1, адрес мипов 0 |

### Данные текстуры

- Блоки DXT5 4×4 по 16 байт: 512×256 → 128×64 блоков = 131 072 байт, 512×512 → 262 144,
  256×128 → 32 768. Обе стороны кратны 32 блокам — в тайлинге нет добивки, размер ровно w·h.
- **Тайлинг Xenos** (как `XGAddress2DTiledOffset`, байт на блок 16, `log2 = 4`, pitch в
  блоках — 128 или 64):

  ```python
  macro = ((x >> 5) + (y >> 5) * (pitch >> 5)) << (4 + 7)
  micro = ((x & 7) + ((y & 0xE) << 2)) << 4
  off = macro + ((micro & ~0xF) << 1) + (micro & 0xF) + ((y & 1) << 4)
  off = ((off & ~0x1FF) << 3) + ((y & 16) << 7) + ((off & 0x1C0) << 2) \
        + (((((y & 8) >> 2) + (x >> 3)) & 3) << 6) + (off & 0x3F)
  ```
- **8in16**: в каждом 16-битном слове байты переставлены (у блока DXT5 меняются местами
  alpha0 и alpha1, байты в парах индексов альфы, color0 и color1 становятся big-endian, в
  32-битном слове индексов цвета — байты в каждой половине). После перестановки и раскладки —
  обычный DXT5 (BC3) как на PC; цвет в BC3 всегда 4 оттенка, кодировщик всё равно держит
  color0 > color1.

### RefPack (запись `2`, иногда `0`)

Заголовок `10 FB` + 3 байта BE — размер распакованного (`02 00 60` = 131 168). Команды:

| Первый байт | Длина | Литералы | Копия | Смещение |
|---|---|---|---|---|
| `0x00–0x7F` | 2 | `b0 & 3` | `((b0 >> 2) & 7) + 3` (3–10) | `((b0 & 0x60) << 3) + b1 + 1` (≤ 1 КБ) |
| `0x80–0xBF` | 3 | `b1 >> 6` | `(b0 & 0x3F) + 4` (4–67) | `((b1 & 0x3F) << 8) + b2 + 1` (≤ 16 КБ) |
| `0xC0–0xDF` | 4 | `b0 & 3` | `((b0 & 0x0C) << 6) + b3 + 5` (5–1028) | `((b0 & 0x10) << 12) + (b1 << 8) + b2 + 1` (≤ 128 КБ) |
| `0xE0–0xFB` | 1 | `((b0 & 0x1F) + 1) · 4` (4–112) | — | — |
| `0xFC–0xFF` | 1 | `b0 & 3`, конец | — | — |

Сжатие 131 168 → ~23 КБ: прозрачные блоки одинаковые.

### Картинка

- Альфа **прямая** (не premultiplied: на краях RGB больше альфы), под альфой 0 цвет чёрный,
  целиком прозрачные блоки — нули. Фон прозрачный.
- Кадр EA (медиана по 40 случайным фото): макушка на y ≈ 15 (большие) / 11 (малые), центр
  головы x ≈ 234 / 101, ширина головы ≈ 149 / 72, шея ≈ 100 / 50, плечи с y ≈ 214 / 114.
- Большие: плечи уходят в прозрачность плавно с y ≈ 232 до 249 (у 467×260 — 241…250),
  последние строки сцены пустые. Малые: обрезаны по нижнему краю без затухания.
- Силуэты p60000…p60003 — тёмно-серая голова (альфа ≤ 191) с четырьмя разными причёсками.

### Что нужно для нормального показа (чек-лист)

1. Путь `fe\ion\artassets\playerheads[small]\<папка по artid>\p<artid>.big` — **оба** размера.
2. BIGF: те же 6 записей, имена — номера символов из Apt Data шаблона, выравнивание 0x40,
   размер LE, метка шаблона, 16 байт хвоста.
3. Apt Data, геометрия и константы — без изменений из настоящего файла (сцена и номера символов
   согласованы между собой).
4. Заголовок XPR2 (0x60 байт) — из шаблона того же размера: DXT5, тайлинг, 8in16, без мипов.
5. Данные — ровно 131 072 / 262 144 / 32 768 байт, блоки разложены тайлингом и переставлены 8in16.
6. Текстура сжата RefPack (как у всех оригиналов; несжатую загрузчик, видимо, тоже примет —
   Apt Data бывает и так, и так, — но не проверено).
7. Картинка — на сцене, остальное прозрачное-чёрное; прямая альфа.
8. В базе `hasportrait = 1` и тот же `artid`; номер — не больше 16383.
9. Размер файла — в пределах оригиналов (до 34 672 / 10 992 байт; наши — 24–29 и 7,5–9,3 КБ).

## 4. Прототип `tools/playerhead.py`

```bash
python tools/playerhead.py info FILE.big…                          # записи, сцена, константа выборки
python tools/playerhead.py decode FILE.big OUT.png [--full] [--dds OUT.dds]
python tools/playerhead.py encode IN.png|IN.dds TEMPLATE.big OUT.big [--trailer md5]
python tools/playerhead.py roundtrip [--deep] FILE_OR_DIR…
python tools/playerhead.py compose MUG.png ARTID OUTDIR [--kind big,small] [--preview DIR] [--auto]
```

- `decode` — сцена (467×253 и т. п.) или вся текстура в PNG RGBA, по желанию DDS DXT5 (линейный).
- `encode` — PNG размера сцены или текстуры (или DDS DXT5 того же размера) в `.big` по шаблону:
  остальные записи, заголовок XPR2, метка и хвост — из шаблона (`--trailer md5` — новый хвост).
- `compose` — портрет НХЛ → оба размера в дереве `OUTDIR/fe/ion/artassets/…` (как в `cache:`).
  Шаблон — оригинал с тем же номером, если есть (тот же вариант 512×512/512×256 и хвост),
  иначе `p1.big` (512×256, символы 2 и 3; хвост — MD5 нового файла).
- `roundtrip` — проверка понимания формата (ниже).

Свои части: RefPack (распаковка и жадный LZ77 с цепочками), BIGF, XPR2, тайлинг, DXT5
(декодер; кодировщик — главная ось + уточнение наименьшими квадратами, альфа в режимах 8 и
6 значений, цвет подбирается по видимым пикселям), PNG (все типы, Adam7), DDS, Lanczos-3
с премножением альфы.

**Проверки (07.10.2026):**

| Что | Результат |
|---|---|
| разбор → сборка BIGF, все 13 851 файл (большие, малые, карты) | байт-в-байт, 0 ошибок |
| тайлинг туда-обратно + 8in16, все 13 851 | 0 ошибок (5 мин 51 с) |
| свой RefPack → распаковка (`--deep`: 14 оригиналов и 6 своих файлов) | совпадает; поток на 0,3–9 % длиннее, чем у EA |

## 6. Компоновка: портрет НХЛ → кадр EA

Замер по 40 случайным фото каждого размера против 8 портретов НХЛ (медианы):

| | большие EA | малые EA | НХЛ 336 |
|---|---:|---:|---:|
| макушка, y | 15 | 11 | 71,5 |
| ширина головы | 149 | 72 | 110 |
| ширина шеи | 100 | 50 | 70,5 |
| макушка → плечи | 199 | 103 | 154 |
| центр головы, x | 234 | 101 | 167 |

Масштаб по ширине головы, шеи и высоте «макушка — плечи»: **1,36** для больших (1,29–1,42) и
**0,67** для малых (0,66–0,71) — то есть большие увеличивают портрет 336 px. В
`tools/playerhead.py` (`LAYOUT`): макушка НХЛ (71,5) → y 15 / 11, центр головы (167,5) →
x 234 / 101, Lanczos-3 с премножением альфы; у больших плечи плавно гаснут на строках
230…250 (smoothstep, как у EA), у малых — обрез по краю. По умолчанию кадр НХЛ берётся как
есть (у НХЛ постановка постоянная), `--auto` — по найденной макушке. Вид — `out/preview/compare.png`.

## 7. План конвейера

1. **Сопоставление.** Уже есть: `write.json` конвейера (`players[]`: `nhl_id`, `row`,
   `game_id`, `artid`, `new`) и `players.json` (`photo`). Своё сопоставление не нужно.
2. **Номера.** Оставить `artid` как назначил конвейер (`artid-registry.json`, стабильны между
   прогонами):
   - 146 игроков NHL 13 — их ID EA ≤ 9802: файл с тем же номером **заменяет** фото 2012 года
     (шаблон — сам оригинал);
   - 632 новых с 9803…12000 → `p8001_12000/p<artid>.big` (номеров там нет — новые файлы);
   - 20 новых с 12001…15488 → `silhouettes/p<artid>.big` (по коду `getArtAssetPath`). Если в
     игре это не сработает — ограничить в `tools/roster/write.py` `ART_MAX = 12000` (в 9803…12000
     свободно ещё ~1500 номеров) и пересобрать базу.
   - Один `artid` с `hasportrait = 1` — один игрок (реестр это и так держит); с силуэтами
     60000+, картами HUT и персоналом не пересекается.
3. **Загрузка** (`fetch --only photos`): `game/work/roster-cache/photos/20262027/<nhl_id>.png`
   через `common.Http` (кэш, пауза ≥ 1 с, повтор на 429/5xx), **без перехода по 302** (или
   проверка итогового адреса на `default-skater`/`default-goalie`) — отметка `.default`.
   798 запросов ≈ 80 МБ, ≥ 14 мин.
4. **Сборка** (новый этап `photos`): `playerhead.compose` для каждого → дерево
   `game/work/<work>/photos/fe/ion/artassets/playerheads[small]/…` + `photos.json` (кто, какой
   `artid`, какие файлы, статус: ok / default / нет PNG). ≈ 2 с на игрока: 27 мин на одном
   ядре, с `multiprocessing.Pool` — минуты. Итог — 1596 файлов: ≈ 21 МБ больших (24–29 КБ
   штука) + 6,5 МБ малых (7,5–9,3 КБ), ≈ 28 МБ.
   В отчёт — лист превью (как `compare.png`) по клубам для глазной проверки.
5. **База.** В `write` (или отдельным шагом поверх выходной базы): `hasportrait = 1` тем, у кого
   статус ok; `hasportrait = 0` — у кого фото нет (силуэт `60000 + artid % 4`). У игроков NHL 13
   без нового фото можно оставить 1 и старое фото 2012 года — выбор политики.
   Поля: `exhibitionplayerbiotable.artid` (уже), `hasportrait`. Сейвы франшизы несут
   `leagueplayerbiotable` со своими `artid`/`hasportrait`: новые франшизы и «Играть сейчас»
   берут из `nhlng.db`, в начатых — править сейв `tools/tdb.py` (по тем же строкам).
6. **Установка** (вручную, как база): `photos/fe/…` → `game/userdata/cache/guest/fe/…`.
   Перепаковывать `nocacherender.big` (1,6 ГБ) и `cache.big` не нужно. Откат — удалить файлы.
7. **Кому фото нет.** АХЛ, юниоры, Европа и новички без съёмки — силуэт игры
   (`hasportrait = 0`); старые фото остальных строк базы (2012 года) не трогаем. Позже — свои
   источники для АХЛ, если понадобится.

## 8. Проверка в игре (когда будет можно)

1. Сохранить `game/userdata/cache/guest/db/nhlng.db`; положить `game/work/photos/out/db/nhlng.db`
   и `nhlng-meta.xml` туда же, дерево `game/work/photos/out/fe` — в `game/userdata/cache/guest/fe`.
2. «Играть сейчас»: «Анахайм» — «Вашингтон» (Карлссон, Томпсон) или «Питтсбург» (Кросби) —
   экран стартовых составов (большие), карточка игрока; составы/обмены (малые).
3. В `port/out/game-release.log` строки `NtCreateFile FAILED` для этих путей пропадут.
4. Отдельно проверить номер > 12000 (Томпсон, `silhouettes/p12241.big`) и новый номер без
   файла в архиве (Карлссон, p10333).
5. Откат — вернуть базу и удалить добавленные файлы.

## 9. Открытые вопросы

- 16 байт хвоста BIGF: назначение неизвестно (не MD5/SHA содержимого и пути). Сейчас — хвост
  оригинала при замене и MD5 нового файла для новых номеров. Если игра их сверяет (не похоже:
  в размер BIGF хвост не входит) — это всплывёт при проверке в игре.
- Свободные файлы с номерами, которых нет в архивах (p9803+), и путь `silhouettes/` для
  номеров > 12000 — по коду должны работать, в игре не проверено.
- Окно малых фото 128×128 со сдвигом 26 показывает x 26…154 сцены; центр головы у EA и у нас —
  x ≈ 101, то есть голова в этом окне чуть правее середины, как и в оригинале.
- Как экраны без явного типа (панели игрока, бокс-скор, календарь) выбирают размер — через
  стиль `NHLPlayerHeadLoader`/`NHLImageLoader`; по каждому экрану не разбиралось.
